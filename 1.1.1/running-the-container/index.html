    Running the container

    Running the container#

    Most people run the whole pipeline in one docker run (or podman run) call and never install tetrapy themselves. This page covers the container: Docker vs Podman, Windows, how a container call is put together, building the image, and the volume contract. The rest of the site documents tetrapy itself.

    Try it in a codespace#

    A guided walkthrough: run Tetracorder over a 300x150 window of a real EMIT L2A scene, one step at a time, and see the mineral maps at the end. No install, no configuration; about ten minutes of which nine are the run itself.

    The badge above opens a GitHub codespace of the repo. The terminal banner tells you how to start the demo (.devcontainer/get-started.sh), which then walks you through tetracorder-lite one step at a time. See .devcontainer/README.md for specific details of how it all works.

    Docker or Podman#

    Either works. Podman implements the same command-line interface, so every example below runs unchanged under podman — substitute the command name and nothing else. The only additions Podman ever needs are volume suffixes on SELinux systems, covered below.

    Install — follow the official instructions, they change more often than this file does:

    Docker Podman
    Windows WSL containers (wslc, recommended; see below) or Docker Desktop Podman Desktop
    macOS Docker Desktop Podman Desktop
    Linux Docker Engine Podman

    Windows#

    Every option on Windows runs Linux containers in a WSL 2 virtual machine.

    Recommended: WSL containers (wslc). Since September 2026, WSL includes its own container engine, so there is nothing else to install and no Docker Desktop licence to consider. You need WSL 2.9.3 or later. From PowerShell:

    wsl --install      # first time only, then reboot
wsl --update
wslc version

    Run the examples in this README from PowerShell, with wslc in place of docker.

    For performance, write /output to a named volume rather than a Windows folder (see where /output lives):

    wslc volume create --driver vhd -o SizeBytes=20000000000 tetra-out
wslc run --rm -v C:\path\to\scenes:/data -v tetra-out:/output `
  tetracorder-lite tetrapy run config.yml `
    --data.rfl /data/<scene>_rfl --data.rfluncert /data/<scene>_uncert
# copy the results out in one pass
wslc run --rm -v tetra-out:/output -v C:\path\to\results:/host `
  tetracorder-lite cp -a /output/. /host/

    Alternatives: Docker Desktop or Podman Desktop. Install either one, and turn on Docker Desktop's Settings → Resources → WSL integration for your distribution. Then run docker or podman from inside the WSL shell, and keep scenes and output under your WSL home (/home/you/...), not /mnt/c/.... You can still reach those files from Explorer at \\wsl$\Ubuntu\home\you.

    Details: WSL containers · WSL install · Docker Desktop WSL 2 backend · Podman on WSL

    Architecture#

    Tetracorder-lite images are provided for both linux/amd64 and linux/arm64, so modern platforms should pull the correct image. If you need a specific architecture, for instance to compare results under emulation, ask for it as usual:

    --platform=linux/amd64

    If you are using Podman#

    Nothing in the examples changes — --rm, -v, -e and the rest mean the same thing to both. Two things are worth knowing anyway:

    • SELinux (Fedora, RHEL, CentOS): add :z to bind mounts, as in -v /path/to/input:/data:z. Without it the container cannot read the mount. This is the one flag Docker has no equivalent for.
    • Rootless: files written to /output come back owned by you, not by root, which is usually what you want.

    Quick start#

    Most people run the whole pipeline in one container call and never install tetrapy themselves. Put the scene's ENVI files in one directory and run:

    docker run --rm \
  -v /path/to/scenes:/data \
  -v tetra-out:/output \
  tetracorder-lite \
  tetrapy run config.yml \
    --data.rfl       /data/<scene>_rfl \
    --data.rfluncert /data/<scene>_uncert \
    --data.glt       /data/<scene>_glt

    This convolves the spectral library onto the scene's wavelength grid, runs Tetracorder, writes COGs, and aggregates the result into L2B mineral products under /output/test/. Point --data.* at the data files, not the .hdrs. The examples use tetracorder-lite as the image name, which is the tag Building the container produces. If your image has a different name, use that instead.

    tetra-out is a named volume, which is the fast choice on macOS and Windows. Copy the results out when the run finishes. See where /output lives. On Linux you can bind-mount a host directory, for example -v /path/to/output:/output.

    Running the container#

    How a container call is put together#

    Every call has the same two halves. Everything up to and including the image name is the container method: which engine, which mounts, which image. Everything after the image name is the command that runs inside the container:

    docker run --rm -v …:/data -v …:/output IMAGE  tetrapy <command> config.yml [--key value …]
└───────────── container method ────────────┘  └───────── runs inside the container ──────┘
    Part What it is
    docker run --rm Engine. podman run --rm works the same way (see Docker or Podman)
    -v …:/data Your input scenes. Read-only access is enough
    -v …:/output Where results are written
    IMAGE tetracorder-lite in these examples; substitute your image's name
    tetrapy <command> The command to run. The image's default command is bare tetrapy, and anything you put after the image name replaces it, so tetrapy must be typed out
    config.yml The default config baked into the image (at /root/config.yml, the working directory)
    --key value Overrides for any config value (see below)

    The rest of this README shows commands in their short form, such as tetrapy run config.yml … or tetrapy aggregate config.yml. Run them by putting your container method in front, exactly as in the Quick start. Mounts and engine flags go before the image name. Config overrides go after config.yml.

    Common options#

    Add these after config.yml. Quote any value that contains spaces, so your shell passes it as a single argument.

    Option Effect
    --output.base /output/<run> Writes this run under its own directory. Tetracorder's output directory is wiped at the start of each run, so give each run its own base if you want to keep earlier results
    --data.glt "" No GLT. COGs are written in raw instrument geometry instead of being orthorectified
    --sensor.deleted_channels.wavelengths "[[…], …]" Wavelength ranges to delete (water bands, detector edges). tetrapy converts them to channel numbers using the scene's own grid; see the non-EMIT example below
    --<stage>.enabled False Skips a pipeline stage, such as --postprocess.enabled False (see The pipeline)

    To check the resolved config without running anything, replace run with preview:

    docker run --rm tetracorder-lite \
  tetrapy preview config.yml --output.base /output/run2

    Example: a non-EMIT sensor#

    Tetracorder takes deleted channels as integer channel numbers. tetrapy lets you give them as wavelength ranges instead: the sensor stage converts each range to channel numbers using the band centres in the scene's .hdr, so the same ranges work on any sensor.

    Anything in sensor.deleted_channels.channels is deleted in addition to the ranges, and the default config sets it, so set it to None when you supply your own wavelengths:

    docker run --rm \
  -v /path/to/scenes:/data \
  -v tetra-out:/output \
  tetracorder-lite \
  tetrapy run config.yml \
    --data.rfl       /data/<scene>_rfl \
    --data.rfluncert /data/<scene>_uncert \
    --data.glt       "" \
    --output.base    /output/aviris-ng \
    --sensor.deleted_channels.units       nm \
    --sensor.deleted_channels.wavelengths "[[365, 400], [1340, 1460], [1790, 1960], [2450, 2520]]" \
    --sensor.deleted_channels.channels    None

    Ranges are inclusive and in units (um by default, or nm). The ranges above are illustrative, so tune them for your instrument. The sensor stage logs the channels it resolved, and Deleted channels covers the full syntax.

    Using your own config#

    For repeated runs of the same kind, for example one sensor, copy config.yml, edit it, and mount it into the container:

    docker run --rm \
  -v /path/to/scenes:/data \
  -v tetra-out:/output \
  -v "$PWD/config.aviris.yml:/config/config.aviris.yml:ro" \
  tetracorder-lite \
  tetrapy run /config/config.aviris.yml --data.rfl /data/<scene>_rfl

    Overrides still apply on top of a mounted config.

    Building the container#

    docker build -f Containerfile -t tetracorder-lite .

    The image compiles specpr + Tetracorder (Fortran/ratfor) and DaVinci (C), then sets up the tetrapy Python environment with uv. DaVinci builds from the vendored source in vendor/davinci in a separate stage, so the compilers and source do not end up in the finished image.

    The build is native on both amd64 and arm64, so nothing here is emulated. To build for the architecture you are not on, which is emulated and much slower:

    docker buildx build --platform=linux/arm64 -f Containerfile -t tetracorder-lite .

    Volume contract#

    Mount point Purpose
    /data Input: reflectance + uncertainty (ENVI format with .hdr; the reflectance header supplies the target grid) and optional GLT
    /output Output: tetracorder results, COGs, and aggregated L2B products
    /conv Optional: convolved libraries (written inside the container unless mounted)

    The unconvolved master libraries (splib06b, sprlb06b; ~24 MB total) are baked into the image at /root/tetracorder/sl1/usgs/library06.conv/, so a normal run only needs the scene mounted at /data. The convolve stage reads its target wavelength/FWHM grid from the reflectance ENVI header (${data.rfl}.hdr), so the convolved library self-consistently matches the scene.

    On macOS and Windows, where /output lives changes the runtime#

    A full scene writes 8,516 files. On Linux that costs nothing — the daemon shares your kernel and a bind mount is an ordinary path. On macOS and Windows every container runs inside a Linux VM, and a bind mount of a host directory crosses a file-sharing layer that charges per filesystem operation. Thousands of small creates, writes, gzips and renames is the worst possible shape for it.

    Measured on an M5 Max under Colima (4 CPU, virtiofs), full EMIT granule emit20250327t212148, 1242x1280x285, everything else held constant:

    /output on total tetrun CPU
    a named volume 6m 42s 5m 58s 200%
    a host bind mount 24m 23s 23m 31s 71%

    Same image, same scene, byte-identical agg.nc — 3.6x, purely from where the output went. The CPU column is the tell: on the volume the run never drops below one core, on the bind mount it sits under one core 79% of the time with the rest idle, waiting on the filesystem. Raising the VM's CPU allocation does not help, because cores were never the constraint.

    So on macOS and Windows, write to a volume and copy out at the end:

    docker volume create tetra-out
docker run --rm -v /path/to/input:/data -v tetra-out:/output \
  tetracorder-lite tetrapy run config.yml \
    --data.rfl /data/<scene>_rfl --data.rfluncert /data/<scene>_uncert
# one bulk pass, ~11 s for 1.8 GB -- the cost is per-operation, not per-byte
docker run --rm -v tetra-out:/output -v "$PWD/results:/host" \
  tetracorder-lite cp -a /output/. /host/

    Input can stay bind-mounted: it is two large sequential reads, which this layer handles fine.

    On Windows, the Windows section shows the same pattern with wslc volume create. Under Docker Desktop or Podman, keeping data in your WSL home rather than /mnt/c/... avoids the much more expensive crossing into NTFS, but a named volume is still the safer choice. On Linux, ignore all of this and bind-mount whatever you like.
